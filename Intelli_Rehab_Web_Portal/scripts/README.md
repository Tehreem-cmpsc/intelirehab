# Database scripts

There is no migration runner: these are run by hand, in the Supabase SQL editor. Almost all are idempotent
(safe to run again). The order below respects every "run after..." that the scripts themselves state; where a
script states nothing, it is placed after the tables it touches.

This is for a **brand-new project**. The live database already has everything up to the last item that was run:
`supabase_full_schema_snapshot.sql` documents what it contains.

| # | Script | What it does |
|---|---|---|
| 0 | `supabase_setup.sql` | Fresh **development** database only: resets clinics and physiotherapists. Refuses to run if either already holds data. |
| 1 | `supabase_core_tables.sql` | Patients, sessions, exercises and the RLS helper functions (`is_physio_of_patient` and friends). Everything below depends on it. |
| 2 | `supabase_full_schema_snapshot.sql` | The rest of the live schema, captured from the live project. Depends on 1. |
| 3 | `supabase_credentialing_and_approval.sql` | Physiotherapist credentialing columns (CNIC, qualification, experience, joining date) and lets admins approve physiotherapists. |
| 4 | `supabase_rls_hardening.sql` | Follow-up hardening after the schema audit (for example, patients can no longer award themselves badges). Run after 3. |
| 5 | `supabase_fix_rls_recursion.sql` | Fixes the "infinite recursion detected in policy" between the clinics and physiotherapists policies. |
| 6 | `supabase_first_login_password_reset.sql` | Forces a physiotherapist to set their own password on first login. |
| 7 | `supabase_rehabilitation_plan_fields.sql` | Adds `status` and `version_no` to rehabilitation plans, as the design document describes. |
| 8 | `supabase_assign_session_rpc.sql` | Assigning an exercise session as one transaction. Run after 1 and 7. |
| 9 | `supabase_seed_exercises.sql` | The exercise catalogue (no duplicates if run twice). |
| 10 | `supabase_exercise_media.sql` | Exercise illustrations. Generated by `generate_exercise_illustrations.py`; run after 9. |
| 11 | `supabase_patient_self_registration.sql` | Lets the mobile app link a patient's own login to their patient record. |
| 12 | `supabase_patient_onboarding.sql` | Onboarding RPCs for the mobile app. |
| 13 | `supabase_patient_onboarding_v2.sql` | "Your injury" answers. Run after 12. |
| 14 | `supabase_patient_choose_clinic_physio.sql` | Choosing a clinic and then a physiotherapist at it. Run after 12. |
| 15 | `supabase_patient_profile_self_edit.sql` | Patients editing their own profile. |
| 16 | `supabase_patient_delete_account.sql` | Patients deleting their own account. |
| 17 | `supabase_patient_wearable_sync.sql` | Keeps `patients.wearable_connected` in step. Run after 2. |
| 18 | `supabase_wearable_presence.sql` | Live wearable connectivity. Run after 2. |
| 19 | `supabase_movement_analysis_activation.sql` | `movement_analysis.muscle_activation`. |
| 20 | `supabase_session_duration.sql` | `sessions.duration_seconds`. |
| 21 | `supabase_session_motion.sql` | Per-session movement recording for the replay. Run after 1. |
| 22 | `supabase_session_module_v2.sql` | Per-set results, pain and early-end reason, per-patient safety limits, the clinic's at-risk rules. Run after 1 and 21. |
| 23 | `supabase_warning_autoclear.sql` | Warnings erase themselves after the patient's next session, with a log, a "seen" receipt, and warned patients leaving the At Risk list. Run after 1. |
| 24 | `supabase_security_hardening.sql` | Security hardening before deployment. The script itself says: run once, **after every other script**, so it stays last. |

Both apps keep working if the newest scripts (20 to 23) have not been run yet: the columns and tables they add are
read defensively, and the features simply do nothing until the script is run.

`src/scripts.readme.test.js` fails if a `supabase_*.sql` file is added here without being listed in this table, so the
order cannot quietly drift.
